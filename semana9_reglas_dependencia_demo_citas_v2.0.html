Reglas de dependencia en la aplicación de reserva de citas

La aplicación ya pasó de cliente-servidor a n-capas. El trabajo de esta semana es identificar las dependencias que permanecen rígidas y reducirlas sin cambiar las rutas HTTP, el cliente ni el esquema de datos.

1. De cliente-servidor a reglas de dependencia

El repositorio actual conserva la arquitectura cliente-servidor: public/index.html se comunica por HTTP con Express y el servidor consulta PostgreSQL en Supabase. El refactor en capas cambió la organización interna, sin modificar esos límites de red.

Pregunta central: si mañana reemplazamos PostgreSQL por un repositorio simulado para hacer pruebas, ¿cuántos archivos de negocio habría que cambiar?

Con el código actual, tendríamos que intervenir un archivo de aplicación: src/aplicacion/citaService.js. Este servicio importa directamente citaRepository.js y profesionalRepository.js, que utilizan PostgreSQL. Para sustituirlos manualmente por repositorios simulados habría que cambiar esas referencias. Las reglas puras de reglasDeAgenda.js no necesitan modificaciones.

Después de aplicar DIP e inyección de dependencias, la respuesta sería: cero archivos de negocio. citaService.js recibiría los repositorios por parámetros y utilizaría sus operaciones (listarTodas, existeEnHorario, guardar y listarTodos) sin conocer si los datos vienen de PostgreSQL o de memoria.

Esquema simplificado: prueba sin PostgreSQL (ejemplo completo en el punto 6)
// Los repositorios simulados se preparan en el archivo de pruebas.
const servicio = crearCitaService({
  citaRepository: repositorioCitasEnMemoria,
  profesionalRepository: profesionalesEnMemoria
});

// El servicio ejecuta las mismas reglas de negocio.
await servicio.reservarCita(datosDePrueba);

¿Qué sí habría que cambiar? Preparar los repositorios simulados y entregarlos al servicio desde la prueba. Si el cambio fuera para toda la aplicación en ejecución, se ajustaría el ensamblaje en server.js y, cuando corresponda, el adaptador de persistencia; no la lógica de aplicación ni las reglas del dominio.

Buscamos que cambiar la tecnología de persistencia no obligue a modificar la lógica de negocio. «Cero» se refiere a los archivos de aplicación y dominio, no a todos los archivos del proyecto. Ambas implementaciones deben respetar el mismo contrato y comportamiento esperado.

Ejemplo resuelto con notación UML 2.x

Usaremos un diagrama de dependencias entre artefactos. Cada rectángulo representa un módulo de código de la aplicación, identificado con «artifact». La relación UML se dibuja con línea discontinua y punta abierta, desde el cliente (módulo dependiente) hacia el proveedor (módulo utilizado). El estereotipo o palabra clave «use» indica una dependencia de uso.

Dependencia de uso existente Dependencia hacia un adaptador concreto Uso del servicio recibido por DI
Precisión UML y JavaScript: «use» no es sinónimo de require(): UML expresa que un elemento necesita o utiliza otro, aunque la referencia se reciba por parámetros. Por otra parte, el contrato de JavaScript se verifica por la presencia de métodos; como el adaptador no declara formalmente implements, no se dibuja una flecha de realización de interfaz que el código no tenga.

Cómo elaborar el diagrama del equipo

  1. Identificar los módulos reales: comenzar por server.js, presentación, aplicación, dominio y persistencia dentro de su propio repositorio.
  2. Examinar require(): si el módulo A importa B, dibujar una dependencia UML con la punta hacia B.
  3. Detectar el acoplamiento: resaltar las dependencias desde aplicación hacia repositorios concretos, no todas las relaciones hacia otros módulos.
  4. Proponer la inversión: quitar las importaciones concretas del servicio, definir las operaciones esperadas y mostrar dónde server.js ensambla las dependencias.
  5. Justificar las relaciones: escribir junto al diagrama qué importación, uso o inyección respalda cada flecha, incluida cualquier diferencia respecto al repositorio de referencia.

Para este ejercicio basta con el tipo UML Dependency y, donde agregue claridad, la palabra clave «use». No corresponde poner «create» en la relación servicio–repositorio, porque el servicio propuesto no crea ese objeto; lo recibe. «call» se refiere a invocaciones específicas y no aporta claridad a este diagrama de módulos. «permit» es ajeno a las relaciones que estamos analizando. Referencia de notación: OMG, UML 2.5.1, sección de dependencias.

Precisión de JavaScript: un objeto que exporta métodos constituye una API, pero eso no implica por sí solo inversión de dependencias. Para aplicar DIP, la aplicación debe dejar de importar la implementación concreta y trabajar contra las operaciones que necesita.

4. DIP e DI: dos decisiones distintas

DIP: principio

La aplicación no debe depender de implementaciones concretas de acceso a datos. Define las operaciones que necesita y recibe algo que las cumple.

DI: mecanismo

Un módulo externo construye o selecciona el repositorio y lo entrega al caso de uso. En esta demo basta una función factoría; no se necesita contenedor IoC.

El repositorio ya tiene una buena separación de responsabilidades. Para completar este paso se puede aprovechar que citaRepository.js exporta listarTodas(), existeEnHorario() y guardar(). Conservaremos esos nombres y las consultas SQL.

Paso 1. Explicitar el contrato de repositorios

En JavaScript no existe una interfaz nativa como en Java o TypeScript. Aquí se emplea un contrato estructural con comprobación básica de métodos. Esto no garantiza toda la semántica del repositorio, pero sí detecta implementaciones incompletas al ensamblar.

PROPUESTA: archivo nuevo src/aplicacion/contratos/repositorios.js
// NUEVO: src/aplicacion/contratos/repositorios.js
// Contrato de colaboración de la aplicación (JavaScript).
function exigirMetodos(objeto, metodos, nombre) {
  for (const metodo of metodos) {
    if (typeof objeto?.[metodo] !== 'function') {
      throw new TypeError(`${nombre} debe implementar ${metodo}()`);
    }
  }
}

function verificarRepositorios({ citaRepository, profesionalRepository }) {
  exigirMetodos(citaRepository,
    ['listarTodas', 'existeEnHorario', 'guardar'], 'citaRepository');
  exigirMetodos(profesionalRepository,
    ['listarTodos'], 'profesionalRepository');
}

module.exports = { verificarRepositorios };

Paso 2. Inyectar los repositorios al servicio

La lógica y el comportamiento de las reglas se mantienen. Lo que desaparece son los require('../persistencia/...') dentro de aplicación.

PROPUESTA: sustituye src/aplicacion/citaService.js
// MODIFICAR: src/aplicacion/citaService.js
const reglas = require('../dominio/reglasDeAgenda');
const { verificarRepositorios } = require('./contratos/repositorios');

function crearCitaService({ citaRepository, profesionalRepository,
                            reloj = () => new Date() }) {
  verificarRepositorios({ citaRepository, profesionalRepository });
  return {
    consultarCitas: () => citaRepository.listarTodas(),
    consultarProfesionales: () => profesionalRepository.listarTodos(),
    reservarCita: async (datos) => {
      reglas.validarDatosCompletos(datos);
      reglas.validarFechaFutura(datos.fecha_hora, reloj());
      const ocupado = await citaRepository.existeEnHorario(
        datos.profesional_id, datos.fecha_hora
      );
      reglas.validarAgendaLibre(ocupado);
      const id = await citaRepository.guardar(datos);
      return { mensaje: 'Cita creada', id };
    }
  };
}

module.exports = { crearCitaService };

Paso 3. Convertir las rutas en una factoría

Actualmente las rutas Express importan el servicio concreto. Para llevar la inyección hasta el borde HTTP, crearCitasRoutes recibirá el servicio ya construido. Mantendrá /api/salud, /api/profesionales, /api/citas y las respuestas del repositorio real.

Ver el archivo propuesto de rutas (código completo)
PROPUESTA: sustituye src/presentacion/citasRoutes.js
// MODIFICAR: src/presentacion/citasRoutes.js
const express = require('express');
const { ErrorDeNegocio } = require('../dominio/reglasDeAgenda');

function crearCitasRoutes({ citaService }) {
  const router = express.Router();
  const CODIGO_HTTP = {
    DATOS_FALTANTES: 400, FECHA_INVALIDA: 400,
    FECHA_PASADA: 400, AGENDA_OCUPADA: 409
  };
  router.get('/salud', (req, res) =>
    res.json({ estado: 'ok', servidor: 'activo',
               hora: new Date().toISOString() }));
  router.get('/citas', async (req, res) => {
    try { res.json(await citaService.consultarCitas()); }
    catch (e) { console.error(e); res.status(500).json({
      error: 'No se pudo consultar la base de datos' }); }
  });
  router.get('/profesionales', async (req, res) => {
    try { res.json(await citaService.consultarProfesionales()); }
    catch (e) { console.error(e); res.status(500).json({
      error: 'No se pudo consultar la base de datos' }); }
  });
  router.post('/citas', async (req, res) => {
    try {
      const resultado = await citaService.reservarCita(req.body);
      res.status(201).json(resultado);
    } catch (e) {
      if (e instanceof ErrorDeNegocio) {
        res.status(CODIGO_HTTP[e.codigo] || 400).json({ error: e.message });
      } else {
        console.error(e);
        res.status(500).json({ error: 'No se pudo guardar en la base de datos' });
      }
    }
  });
  return router;
}
module.exports = { crearCitasRoutes };

// NUEVO: test/citaService.test.js (Node.js >= 18)
const test = require('node:test');
const assert = require('node:assert/strict');
const { crearCitaService } = require('../src/aplicacion/citaService');

function crearServicioParaPrueba(ocupado = false) {
  let guardadas = 0;
  const servicio = crearCitaService({
    citaRepository: {
      listarTodas: async () => [],
      existeEnHorario: async () => ocupado,
      guardar: async () => { guardadas++; return 7; }
    },
    profesionalRepository: { listarTodos: async () => [] },
    reloj: () => new Date('2026-10-01T00:00:00Z')
  });
  return { servicio, guardadas: () => guardadas };
}

test('reserva permitida', async () => {
  const x = crearServicioParaPrueba();
  const respuesta = await x.servicio.reservarCita({
    paciente: 'Ana', profesional_id: 1,
    fecha_hora: '2026-11-15T10:00:00Z'
  });
  assert.equal(respuesta.id, 7);
  assert.equal(x.guardadas(), 1);
});

test('agenda ocupada no genera escritura', async () => {
  const x = crearServicioParaPrueba(true);
  await assert.rejects(() => x.servicio.reservarCita({
    paciente: 'Ana', profesional_id: 1,
    fecha_hora: '2026-11-15T10:00:00Z'
  }), { codigo: 'AGENDA_OCUPADA' });
  assert.equal(x.guardadas(), 0);
});

test('fecha pasada se rechaza sin consultar PostgreSQL', async () => {
  const x = crearServicioParaPrueba();
  await assert.rejects(() => x.servicio.reservarCita({
    paciente: 'Ana', profesional_id: 1,
    fecha_hora: '2026-09-01T10:00:00Z'
  }), { codigo: 'FECHA_PASADA' });
  assert.equal(x.guardadas(), 0);
});

7. Lo que DIP y DI no solucionan

Concurrencia en la agenda

La versión actual consulta existeEnHorario() y, si no hay conflicto, ejecuta guardar(). Dos peticiones simultáneas pueden encontrar el mismo horario libre y guardar dos citas: es una condición de carrera.

Separar capas e inyectar un repositorio no resuelve esa exclusión. Una solución posterior es establecer una restricción única sobre profesional y fecha-hora, y traducir el error de duplicado a la respuesta HTTP correspondiente.

Ejemplo SQL para una mejora futura (no ejecutar durante el taller)

Seguridad de conexión

El archivo real src/persistencia/db.js utiliza ssl: { rejectUnauthorized: false }. Este ajuste deshabilita la verificación del certificado TLS y debe revisarse antes de utilizar el ejemplo como referencia de producción. No está relacionado con DIP, pero forma parte de la revisión técnica del repositorio.

¿Cuándo no crear más abstracciones?

No se necesita una interfaz por cada función ni una carpeta extra para todo. Conviene introducir contratos cuando una colaboración cruza una frontera arquitectónica y aporta testabilidad o independencia frente a cambios concretos.

Como alternativa reproducible en Windows, Linux o macOS, el siguiente script utiliza fetch, disponible desde Node.js 18, y no requiere instalar otra biblioteca. Genera una fecha futura al ejecutarse, registra una cita y verifica que repetirla devuelve 409.

Archivo nuevo: test/api-smoke.js (verificación HTTP local)
// NUEVO: test/api-smoke.js (Node.js >= 18)
// Solo para una BD propia de pruebas. Este script crea una cita.
const assert = require('node:assert/strict');
const BASE = process.env.BASE_URL || 'http://localhost:3000';

async function solicitar(metodo, ruta, datos) {
  const respuesta = await fetch(`${BASE}${ruta}`, {
    method: metodo,
    headers: datos ? { 'Content-Type': 'application/json' } : {},
    body: datos ? JSON.stringify(datos) : undefined
  });
  const cuerpo = await respuesta.json();
  return { estado: respuesta.status, cuerpo };
}

async function verificar() {
  const salud = await solicitar('GET', '/api/salud');
  assert.equal(salud.estado, 200);
  const prof = await solicitar('GET', '/api/profesionales');
  assert.equal(prof.estado, 200);
  assert.ok(Array.isArray(prof.cuerpo) && prof.cuerpo.length > 0,
    'La BD de pruebas debe contener al menos un profesional');
  const citas = await solicitar('GET', '/api/citas');
  assert.equal(citas.estado, 200);
  assert.ok(Array.isArray(citas.cuerpo));

  const reserva = {
    paciente: 'Prueba Semana 9',
    profesional_id: prof.cuerpo[0].id,
    fecha_hora: new Date(Date.now() + 72 * 60 * 60 * 1000).toISOString()
  };
  const creada = await solicitar('POST', '/api/citas', reserva);
  assert.equal(creada.estado, 201);
  assert.ok(creada.cuerpo.id, 'La creación debe devolver un ID');

  const repetida = await solicitar('POST', '/api/citas', reserva);
  assert.equal(repetida.estado, 409);

  const pasada = await solicitar('POST', '/api/citas', {
    ...reserva,
    fecha_hora: new Date(Date.now() - 24 * 60 * 60 * 1000).toISOString()
  });
  assert.equal(pasada.estado, 400);
  console.log('API comprobada: GET 200, POST 201, 409 y 400.');
}

verificar().catch(error => {
  console.error('Falló la verificación HTTP:', error.message);
  process.exitCode = 1;
});
Terminal 2: ejecutar el script contra localhost
node test/api-smoke.js

La verificación HTTP crea un registro en PostgreSQL. Ejecutarla únicamente sobre una base de datos propia de pruebas; no sobre el servicio común de Render ni sobre una base compartida con otros equipos. El endpoint actual no tiene operación de eliminación: al terminar, retirar el dato de prueba desde Supabase si corresponde y se cuenta con autorización. El resultado 409 se comprueba en peticiones secuenciales; no demuestra seguridad ante solicitudes simultáneas.

Si aparece un error 500, revisar primero el registro de error de la terminal donde se ejecutó npm start, la variable DATABASE_URL, las tablas y los datos de prueba. Las cuatro pruebas unitarias aprobadas no garantizan que PostgreSQL esté configurado. Si un equipo no dispone de una base de datos de pruebas independiente para ejecutar las escrituras 201 y 409, debe consultar con el docente antes de utilizar una base compartida; no debe hacer pruebas de escritura sobre el despliegue común.
