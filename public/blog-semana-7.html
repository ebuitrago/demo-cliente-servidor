cliente-servidor

Instalación del sistema de reserva de citas con Supabase, GitHub y Render

Guía de despliegue paso a paso de una aplicación Cliente-Servidor. Al finalizar, el sistema queda publicado en una URL de acceso libre.

Publicado el 15 Sep 2026 · Última actualización: 21 Sep 2026 · 12 min de lectura

EB
Elias Buitrago BolivarArquitectura de Sistemas I · Universidad Central

1. Introducción

El sistema es una aplicación de reserva de citas construida con el estilo arquitectónico Cliente-Servidor. Está compuesto por tres piezas que residen en lugares físicamente distintos y se comunican por la red:

PiezaFunciónDónde se ejecutaArchivo
ClientePágina web que muestra datos y envía peticiones. No contiene reglas de negocio ni acceso a datos.El navegador de cada personapublic/index.html
ServidorPrograma que recibe peticiones HTTP, aplica las reglas de negocio y consulta la base de datos.Render (nube)server.js
Base de datosAlmacena profesionales y citas. Solo el servidor se conecta a ella.Supabase (nube)db/setup.sql

El siguiente diagrama de contexto muestra los actores y sistemas externos. El usuario se comunica con el sistema por HTTP; el sistema consulta la base de datos por SQL sobre una conexión cifrada; GitHub actúa como origen del código, desde donde Render despliega automáticamente.

Una precisión conceptual antes de continuar: Cliente-Servidor nombra una relación de solicitud y provisión entre dos partes, no una cantidad fija de piezas. En este sistema, el navegador actúa como cliente del servidor Express; y el servidor Express, a su vez, actúa como cliente de PostgreSQL. Un mismo componente puede desempeñar ambos roles según la interacción que se observe.

El diagrama de componentes abre la caja del servidor. En esta versión, los cuatro componentes internos conviven en un solo archivo (server.js); las reglas de negocio, resaltadas en color distinto, se extraerán a su propia capa en la Semana 8.

La instalación consta de tres partes en orden estricto: primero la base de datos (Supabase), luego el código en un repositorio (GitHub) y por último el servidor (Render). Render necesita leer el código desde GitHub, y el servidor necesita la cadena de conexión que entrega Supabase; por eso el orden no puede invertirse. GitHub, Render y Supabase se usan aquí como la infraestructura mínima necesaria para observar el estilo Cliente-Servidor funcionando sobre una red real; el tratamiento formal del despliegue como tema corresponde a semanas posteriores del curso.

2. Requisitos previos

  1. Una cuenta en github.com (gratuita).
  2. Una cuenta en supabase.com (gratuita; permite iniciar sesión con GitHub).
  3. Una cuenta en render.com (gratuita; permite iniciar sesión con GitHub).
  4. Los archivos del proyecto descomprimidos en el computador: server.js, package.json, package-lock.json y las carpetas public/ y db/.

Todo el procedimiento usa los planes gratuitos de los tres servicios y no requiere tarjeta de crédito. El flujo principal se realiza completo desde el navegador; no es necesario instalar programas.

3. Paso 1 — Crear la base de datos en Supabase

3.1 Crear el proyecto

  1. Se ingresa a supabase.com y se inicia sesión (opción Continue with GitHub).
  2. La primera vez, Supabase pide crear una organización: se acepta el nombre sugerido y el plan Free.
  3. Se presiona New project y se completa el formulario:
    • Project name: demo-citas (o el nombre que se prefiera; es solo una etiqueta).
    • Database Password: se inventa una contraseña con solo letras y números, por ejemplo DemoCitas2026arqui. No debe contener @, #, :, / ni otros símbolos, porque la contraseña irá dentro de una URL y los símbolos la rompen. Se copia de inmediato a un bloc de notas: Supabase no la vuelve a mostrar.
    • Region: la más cercana; para Colombia, South America (São Paulo).
  4. Se presiona Create new project y se espera 1 a 2 minutos hasta que el proyecto quede activo.

3.2 Crear las tablas y los datos de ejemplo

  1. En el menú lateral izquierdo se abre SQL Editor.
  2. En el computador se abre el archivo db/setup.sql con Bloc de notas o VS Code, se selecciona todo el contenido y se copia.
  3. Se pega el contenido en el editor de Supabase y se presiona el botón Run.
  4. Aparece una advertencia de destructive operation. Es esperada: el script incluye DROP TABLE IF EXISTS para poder re-ejecutarse desde cero. Se confirma con Run this query.
  5. En el panel inferior debe aparecer una tabla con 2 filas (Carlos Muñoz y María Salazar). Ese resultado confirma que las tablas y los datos quedaron creados.

Verificación opcional: en el menú lateral, Table Editor debe mostrar las tablas profesionales (3 filas) y citas (2 filas).

3.3 Copiar la cadena de conexión

  1. En la barra superior del proyecto se presiona el botón Connect.
  2. Si la ventana abre en la pestaña Framework (con instrucciones de Next.js), se ignora ese contenido y se cambia a la pestaña Direct — Connection string.
  3. Dentro de esa pestaña aparecen tres tipos de conexión. Se copia la URI de la sección Transaction pooler: 
    postgresql://postgres.abcdefghijk:[YOUR-PASSWORD]@aws-0-sa-east-1.pooler.supabase.com:6543/postgres
    Dos señas confirman que es la correcta: termina en el puerto :6543 y el nombre del servidor contiene la palabra pooler. La parte de la región (sa-east-1) puede variar según la región elegida; se copia la cadena propia tal cual.
  4. En el bloc de notas se reemplaza [YOUR-PASSWORD] (incluidos los corchetes) por la contraseña del punto 3.1. La cadena resultante es el valor de DATABASE_URL que se usará en Render.
Advertencia: no se debe usar la opción Direct connection. Esa conexión usa IPv6 y falla desde el plan gratuito de Render. La cadena correcta es siempre la del Transaction pooler.
Seguridad: la cadena completa contiene la contraseña de la base de datos. No debe subirse a GitHub ni compartirse; solo se pega en la configuración de Render.

4. Paso 2 — Subir el código a GitHub

  1. En github.com se presiona el botón + (esquina superior derecha) y luego New repository.
  2. Repository name: demo-citas (nombre libre). Se deja Public y se presiona Create repository.
  3. Se suben los archivos. Según cómo haya quedado el repositorio, aparece una de dos pantallas:
    • Repositorio vacío (no se marcó ninguna casilla al crearlo): se usa el enlace uploading an existing file.
    • Repositorio con README inicial (se marcó Add a README): se usa el botón Add file → Upload files.
  4. En el área de carga se arrastran: server.js, package.json, package-lock.json y las carpetas public/ y db/ completas. Los navegadores modernos aceptan arrastrar carpetas y conservan su estructura.
  5. Se presiona Commit changes y se espera a que termine la carga.
  6. Verificación: en la página principal del repositorio deben verse server.js, package.json y las carpetas public y db.
No se deben subir: el archivo .env (si se creó localmente, contiene la contraseña) ni la carpeta node_modules (miles de archivos de librerías que Render reinstala solo con npm install).

5. Paso 3 — Desplegar el servidor en Render

  1. Se ingresa a render.com y se inicia sesión con GitHub.
  2. Se presiona New + → Web Service.
  3. Si aparece el mensaje No repositories found, falta un permiso que se otorga una sola vez: se presiona el botón GitHub (bajo Configure your Git provider), se elige la cuenta personal, se selecciona All repositories u Only select repositories (marcando demo-citas) y se presiona Install. GitHub devuelve a Render y el repositorio aparece en la lista.
  4. Se selecciona el repositorio demo-citas. Render detecta que es un proyecto Node y autocompleta varios campos. Se verifica el formulario:
    CampoValor
    Namedemo-citas (define la URL final)
    LanguageNode
    Branchmain
    Build Commandnpm install
    Start Commandnode server.js
    Instance TypeFree (si viene preseleccionado un plan pago, se cambia)
  5. Antes de crear el servicio, en la sección Environment Variables se agrega una variable:
    • Key: DATABASE_URL
    • Value: la cadena del Transaction pooler guardada en el Paso 1, con la contraseña ya puesta. Se verifica que no queden los corchetes de [YOUR-PASSWORD].
  6. Se presiona Deploy Web Service. En la pantalla de registros (logs) se observa la descarga del código, la instalación de librerías y, al final, la línea que confirma el arranque: 
    Servidor escuchando en el puerto 10000
  7. En la parte superior aparece la URL pública, con la forma https://demo-citas.onrender.com (si el nombre estaba tomado, Render agrega un sufijo). Al abrirla debe cargar la página de Reserva de Citas mostrando las 2 citas de ejemplo.
Señal de éxito: ver las citas de Carlos Muñoz y María Salazar en la página significa que el circuito completo funciona: los datos viajaron desde Postgres en Supabase, pasando por el servidor Express en Render, hasta el navegador.

6. Verificación funcional

Con el sistema desplegado, se ejecutan cuatro pruebas para confirmar el comportamiento:

  1. Reserva válida: se crea una cita con fecha de mañana. El sistema responde "El servidor aceptó la cita" y la agrega a la tabla, con la misma hora que se eligió.
  2. Regla de fecha pasada: se intenta reservar con fecha de ayer. El servidor la rechaza con el mensaje "no se pueden reservar citas en el pasado".
  3. Regla de agenda: se intenta reservar la misma fecha y hora con el mismo profesional de una cita existente. El servidor responde que ese profesional ya tiene una cita a esa hora.
  4. Múltiples clientes: se abre la misma URL desde un celular. La lista de citas es idéntica a la del computador, porque el servidor es la única fuente de los datos.

Verificación de extremo a extremo: en Supabase, Table Editor → citas debe contener la cita creada en la prueba 1.

7. Pruebas de throughput y velocidad de respuesta

Las siguientes pruebas miden el rendimiento del sistema desplegado con la herramienta autocannon, que genera carga HTTP y reporta peticiones por segundo (throughput) y latencia por percentiles. Es la única sección de esta guía que requiere una terminal con Node.js (versión 18 o superior) instalado; la herramienta se ejecuta con npx, sin instalación adicional.

7.1 Preparación

  1. Se despierta el servicio antes de medir. En el plan gratuito de Render, el primer acceso tras 15 minutos de inactividad tarda 30 a 60 segundos (arranque en frío) y arruina las cifras si se incluye en la medición: 
    curl https://demo-citas.onrender.com/api/salud
    En Windows sin curl, basta abrir esa URL en el navegador y esperar la respuesta JSON.
  2. Se reemplaza demo-citas.onrender.com por la URL propia en todos los comandos.

7.2 Prueba 1 — Latencia base sin base de datos

El endpoint /api/salud responde sin consultar la base de datos. Esta prueba aísla el costo de la red y del servidor Express: 10 conexiones concurrentes durante 20 segundos.

npx autocannon -c 10 -d 20 https://demo-citas.onrender.com/api/salud

7.3 Prueba 2 — Latencia con base de datos

El endpoint /api/citas ejecuta una consulta SQL contra Supabase. La diferencia de latencia frente a la prueba 1 corresponde al costo de ir a la base de datos remota.

npx autocannon -c 10 -d 20 https://demo-citas.onrender.com/api/citas

7.4 Prueba 3 — Escrituras (POST)

Se mide la creación de citas con 5 conexiones durante 15 segundos. Como todas las peticiones llevan el mismo profesional y la misma hora, se espera que una se inserte y las demás reciban el código 409 (regla de agenda ocupada). La prueba permite observar cómo se comporta la regla actual bajo concurrencia — no garantiza exclusión: la implementación verifica la disponibilidad y luego inserta, en dos pasos separados y sin restricción de unicidad en la base de datos, de modo que dos peticiones simultáneas podrían comprobar "libre" al mismo tiempo e insertar ambas (condición de carrera). Garantizar la exclusión requiere una restricción en el nivel de los datos: el índice de unicidad del experimento 7.6.3.

npx autocannon -c 5 -d 15 -m POST -H "Content-Type: application/json" -b "{\"paciente\":\"Prueba Carga\",\"profesional_id\":1,\"fecha_hora\":\"2027-01-01T10:00:00Z\"}" https://demo-citas.onrender.com/api/citas

7.5 Lectura de los resultados

Autocannon imprime dos tablas. Las métricas relevantes son:

MétricaSignificado
Req/SecThroughput: peticiones atendidas por segundo.
Latency p50Mediana: la mitad de las peticiones respondió en ese tiempo o menos.
Latency p97.5 / p99Cola de la distribución: lo que experimentan las peticiones más lentas. Es la métrica honesta del rendimiento; el promedio oculta los casos malos.
2xx / Non-2xxRespuestas exitosas frente a rechazos. En la prueba 3, los Non-2xx son los 409 esperados.

7.6 Experimentos comparativos sugeridos

  1. Costo de la base de datos: se comparan las latencias p50 de las pruebas 1 y 2. La diferencia cuantifica el viaje servidor → Supabase por cada consulta.
  2. Efecto de la geografía: se ejecutan las pruebas con las regiones actuales, se anotan las cifras, se co-ubican Render y Supabase en la misma región (por ejemplo, Virginia y East US) y se repiten las pruebas. La mejora se obtiene sin cambiar una sola línea de código: es una decisión de despliegue físico (tiers), no de organización lógica (layers).
  3. Efecto de una optimización de código: si se reduce el POST de dos consultas SQL a una (índice de unicidad en la base de datos), las pruebas antes y después cuantifican el valor del cambio.
Precauciones: se mantiene la carga baja (-c 10 o menos): los planes gratuitos tienen límites de conexiones y no se busca agotar el pool de Supabase. Al terminar, se eliminan las citas de prueba desde el Table Editor de Supabase.
